# pycdc-rs

English | [简体中文](README.zh-CN.md)

A Python bytecode disassembler and decompiler written in Rust, supporting `.pyc` files from **Python 2.0 – 3.15 (dev)** and restoring them to readable `.py` source.

> **Current verification level**: across 13 interpreters (2.6–3.14) and a corpus of
> 520 real standard-library modules, **semantic equivalence is 520/520 = 100%**
> (398 of them byte-exact at the structured-bytecode-signature level, 76.5%);
> the behavior-equivalence matrix is **490/490 = 100%** (decompiled output run
> under the same interpreter produces identical results to the original);
> all output compiles with zero syntax errors and zero incomplete placeholders.

Design references: [Decompyle++ (pycdc)](https://github.com/zrax/pycdc), [uncompyle6/decompyle3](https://github.com/rocky/python-decompyle3) and [xdis](https://github.com/rocky/python-xdis). Core ideas:

- **Version differences are pure data**: one opcode config table per Python version (JSON, generated by `tools/gen_configs.py` from xdis and the CPython `opcode` module, embedded at compile time; `--opcodes` can override/extend from an external directory).
- **Normalization at the decode layer**: instruction width (variable vs wordcode), EXTENDED_ARG chains, CACHE inline caches, absolute/relative jumps, byte vs code-unit jump targets — all unified in `bytecode.rs`, so the entire decompilation layer above is shared across versions.
- **Stack simulation + block stack** decompilation model (pycdc style): a value stack builds expressions; a block stack plus jump-target intervals recovers if/elif/else, while, for, try, with and friends. Dedicated handling exists for 3.8+ rotated while loops, 3.12+ COPY+conditional-jump boolean chains, 3.12+ PEP 709 inlined comprehensions, 3.11+ exception-table-driven try/except, 3.13+ SET_FUNCTION_ATTRIBUTE, the 3.14 CALL slot changes, and more.
- **Graceful degradation**: unrecognized constructs render as comment placeholders with `WARNING: decompilation incomplete` on stderr — never a crash.

## Build

```sh
cargo build --release
# artifacts: target/release/pycdc (decompiler) and target/release/pycdas (disassembler)
```

Dependencies are only `serde` / `serde_json` / `thiserror`; `build.rs` generates the canonical opcode enum from `configs/opcodes/*.json`.
The release profile enables `opt-level=3` + fat LTO + single codegen unit + `strip`.

## Performance

Measured on Apple Silicon (M series), 526 real `.pyc` files (2.6–3.14 stdlib corpus, ~9.5MB):

| Scenario | Time | Peak memory |
|---|---|---|
| Batch (default parallel, CPU-count workers) | **≈0.05s** | ≈25MB |
| Batch (`-j 1` serial) | ≈0.34s | ≈13MB |
| Largest single file (74KB pyc, incl. process startup) | ≈5.5ms | ≈4.4MB |
| Process startup overhead | ≈2ms | — |

Opcode tables are parsed **lazily per version** (a single-file run parses exactly one table); debug environment-variable flags are cached per call site (`OnceLock`); offset→index maps use a deterministic fast hash; parallel batch output stays in deterministic order. When the pipe reader closes early (`pycdc x.pyc | head`), the process exits quietly instead of panic-printing BrokenPipe.

## Usage

```sh
# single pyc: print to stdout
pycdc program.pyc > program.py

# single pyc: write to a file (-o pointing at an existing directory or ending
# in a path separator writes <name>.py inside that directory)
pycdc program.pyc -o program.py
pycdc program.pyc -o ./outdir/

# batch-decompile a directory (recursive .pyc/.pyo collection): the input
# layout is mirrored into the output directory; parallel by CPU count,
# -j N sets the worker count (-j 1 = serial, lowest memory)
pycdc ./pyc-corpus -o ./src-out
pycdc ./pyc-corpus -o ./src-out -j 4

# batch without -o: the default output directory is a sibling of the input
# named <input-name>-decompiled
pycdc ./pyc-corpus        # creates ./pyc-corpus-decompiled/ (same structure)

# multiple file inputs without -o: <name>.py is written next to each input
pycdc a.pyc b.pyc         # creates a.py, b.py

# misc
pycdc version             # version info (also -V / --version)
pycdc --help              # full help (also -h / help)

# disassembly (exception tables, line numbers, nested code objects)
pycdas program.pyc

# raw marshal data (no pyc header) with an explicit version
pycdc -v 3.8 payload.marshal

# external opcode configs (e.g. adding support for a brand-new Python)
pycdc --opcodes ./my-configs program.pyc
```

## Tests

```sh
cargo test                    # unit + integration tests (tests/pyc/ holds 2.7–3.14 fixtures)
python3 tests/roundtrip.py    # multi-version regression matrix: compile -> decompile -> recompile -> structured bytecode compare
python3 tools/run_behavior.py # behavior-equivalence matrix: run original and decompiled code under the same interpreter, compare output
python3 tools/verify_corpus.py # full 520-module real-corpus verification (see below)
```

`roundtrip.py` / `run_behavior.py` / `verify_corpus.py` require multiple Python
interpreters on the machine (2.6–3.14, installable via pyenv/uv).

## Updating version configs

After a new Python release:

```sh
python3 tools/gen_configs.py --xdis /path/to/python-xdis   # regenerate configs/
cargo build                                                 # re-embed
```

- Tables for 2.0–3.10 and 3.15 come from xdis; 3.11–3.14 are exported natively by `tools/dump_native.py` inside each matching interpreter (including CACHE tables).
- `configs/magics.json` maps magic number → version (~380 entries, including alpha/beta releases and PyPy/GraalPy variants).

## Real-corpus verification (tests/corpus/)

The **bundled standard-library sources** of 13 historical interpreters installed via pyenv/uv (2.6.9, 2.7.18, 3.3.7, 3.5.10, 3.6.15, 3.7.17, 3.8.20, 3.9.25, 3.10.21, 3.11.16, 3.12.14, 3.13.15, 3.14.7) were compiled to `.pyc`; sources and pycs live in per-version directories, **520 modules** total. Verification pipeline (`tools/verify_corpus.py`):

1. `pycdc` decompiles each `.pyc`;
2. the decompiled output is recompiled with the **same-version interpreter**;
3. the original and recompiled pycs are compared by **structured bytecode signature** (opname + argrepr, jump targets normalized to labels);
4. on signature mismatch, `tools/ast_compare.py` performs a **normalized-AST semantic comparison** (run by the same-version interpreter; normalizations: adjacent import merging, global/nonlocal hoisting, `while 1`≡`while True`, terminal-branch else flattening, set/list(genexpr)≡comprehension, numeric constant folding).

Grades: `PASS` (identical bytecode signature) > `AST-PASS` (semantically equivalent AST — the acceptance bar "runnable logic equivalence") > `INCOMPLETE` (compiles but contains placeholder markers or a decompilation-incomplete warning) > `SIG-DIFF` (compiles, structural difference) > `SYNTAX-ERR`.

Current results (520 modules, fully re-verified against the release binary):

| Metric | Count |
|---|---|
| PASS (bytecode-signature identical) | 398 (76.5%) |
| AST-PASS (normalized-AST semantic equivalence) | 122 (23.5%) |
| **Semantic equivalence total** | **520 (100%)** |
| INCOMPLETE (compiles, placeholder/warning) | **0** |
| SIG-DIFF (compiles, structural difference) | **0** |
| SYNTAX-ERR | **0 (all 520 outputs compile under their matching interpreter)** |

## Known limitations

- try/except: 3.11+ rebuilds from the exception table (incl. except*, nested chains, continue/return inside handlers, inline-finally copy pruning in loops, consecutive module-level sibling tries, sunk implicit `return None` normalization for function-tail try/except/else); the 3.8–3.10 SETUP_* era is restored by a chain state machine (incl. nested tries inside handlers, function-tail try/finally, success-path statement ordering, deferred folding when a whole loop body is a chain, closing handlers ending in a bare `RAISE_VARARGS`); multi-handler chains with a trailing bare `except:` are placed correctly, and on 3.11+ a bare `except:` is no longer misread as `finally:`; py2 else-region emission is decided by pre-region provenance and bounded-region statement material. The dead-code-eliminated empty-generator idiom (`while False: yield None`) is synthesized back in postprocessing. Empty `finally: pass` chains (including nested ones) render as real try/finally structure; `finally: return X` swallow shapes are correctly placed in both eras (3.11+ cleanup-path tearing is refolded; ≤3.10 uses the discriminator "the return material sits before the END_FINALLY of the SETUP_FINALLY cleanup region", leaving genuine post-try returns untouched). Known gaps: in 2.x/3.5–3.10 the combination "continue inside an except branch + finally on the same try + inside a loop" can lose loop-nesting structure (can emit a placeholder on 3.10; behavior usually still equivalent); on 3.9/3.10 an inline try inside a with body may flatten and leak `__exit__` protocol calls (behavior-equivalent, with placeholder); bare-except placement can add one semantically-equivalent `continue` at the tail of a handler inside a loop. The current 520-module corpus has zero placeholders and zero warnings.
- `with a, b:` multi-context managers render as nested with statements (semantically equivalent).
- match/case (3.10–3.14): literal/capture/wildcard/or/sequence (incl. `*rest` and literal elements)/mapping (incl. value-literal patterns and `**rest`)/class patterns (positional + keyword + literal subpatterns, incl. the no-subject-COPY shape of a single non-wildcard case)/singletons (True/False/None) and guards are all supported; match inside loops (case bodies jumping back with JUMP_BACKWARD, trailing `case _:` at the failure target) is restored; or-arms render on some versions as multiple cases sharing a body (semantically equivalent). Known gaps: 3.10's legacy per-attribute extraction (BINARY_SUBSCR+ROT stack order), recursive nesting inside pattern slots (e.g. sequence/class patterns inside mapping values), or-expansion between non-literal patterns (sequence|sequence, class|class, incl. shared capture bindings), and the inverted in-loop shape where the last case jumps to its body with PJIF_TRUE and failure uses JUMP_BACKWARD (e.g. `case 2: return`) can be misdetected as a wildcard/condition stub (behavior usually still equivalent).
- 3.14 PEP 649 annotations: function/method-level `__annotate__` is rebuilt into signature annotations via LOAD_FROM_DICT_OR_GLOBALS; module/class-level annotations (including `__conditional_annotations__`-gated conditional ones) are restored to real annotation statements by the `restore_pep649_annotations` postprocess — the `{IDX}` markers leaked by the gate SET_ADD protocol are the original positions (TYPE_CHECKING-block annotations land back inside their block; class-body annotations fold/insert in source order). Runtime `get_annotations` VALUE/FORWARDREF results match the original exactly. Known corner: entries inside dead branches the compiler folded away entirely (annotations under `if False:`) are dropped — VALUE/FORWARDREF semantics still match the original; only the STRING-format annotation dict differs (the original keeps that dead entry's text).
- PEP 750 template strings (3.14+ t-strings, `BUILD_TEMPLATE`) are supported: interpolation, conversion flags and format specs all restore correctly (`t"a{b}c"`, `t"{b!r:>{b}}"`).
- else clauses: the family of root causes that hoisted `try/except/else` and `if/else` bodies out of their `else:` association is fixed, covering three layouts: ① 3.11+ inline handlers (else body JUMP_FORWARDs to the merge); ② legacy (≤3.10) else bodies containing nested try/def/class (block-structuring flush order + else-region boundary routing); ③ 3.12+ outlined handlers (handlers placed after the post-try code, jumping BACKWARD to the merge while the else body flows straight in with no forward-jump delimiter — the merge is inferred from the handler's back-jump target, with "last exception-table fragment" disambiguation for 3.12 inline comprehensions splitting the try body). _bootlocale/copy/_compat_pickle/abc etc. reach PASS or correct nesting. Residual: a few modules (_weakrefset/copy/copyreg 3.3) are semantically equivalent (AST-PASS) but keep a nesting-level difference with empty orelse placement (`orelse=[]` at a different position) — not else-body loss.
- PEP 695/696 type-parameter syntax (3.12+) is supported: `type X[T] = ...` aliases, `def f[T](...)`, `class C[T](...)`, including bounds/constraints (`T: int`, `T: (int, str)`), `*Ts`/`**P`, and PEP 696 defaults (`T = int`, `*Ts = *tuple[()]`, 3.13+). Implementation: the compiler-generated `<generic parameters of X>` wrapper functions are recognized and their CALL_INTRINSIC protocol executed in a nested decompilation.
- Async: async def/await/async for/async with (incl. nesting and multi-context) are supported; known gaps: inlined async comprehensions, the async-generator asend/athrow protocol, and the 3.7 SETUP_EXCEPT-guarded async-for break+else combination.
- Ternary expressions inside comprehension elements (`[a if c else b for ...]`) can be misplaced on some old versions.
- Chained comparisons (`a == b == c`): value position, and-form if conditions (3.8–3.14, via SCC fallback on 3.12+), or-form (`if chain or x[ or y]:`), **chain-or-chain** (`(a==b==c) or (d==e==f)`, incl. the 3.8–3.10 small-block duplication layout and py2 value-form JFOP/JTFOP short-circuits), **negated form** (`if not (a<b<=c): raise/return`, both compiler layouts: 3.10/3.12 tail-copying the body into the else path, 3.8/3.9/3.11/3.13/3.14 cleanup-trampoline sharing), elif contexts, and slice operands (incl. the 3.14 const-slice marshal reference-order fix) are all supported (b23_boolchain 13/13 green).
- py2: `raise T, I[, B]` renders natively (faithful and recompilable, no longer rewritten to call form); py2.6 function-level inline list comprehensions (`_[N]` FAST accumulator) are supported; the deep-nesting shape "if containing an if + sibling elif + dangling tail return" may lose subsequent branches.
- The historical 2.7–3.9 gap where an elif arm containing a nested else-less if followed by another elif (`elif A: (if B: X) elif C: Y`) lost the second arm to jump-threaded and-chain merging has been **re-verified as fixed** — the b28_elifnest case runs green on all 13 interpreters.
- Python 1.x: marshal loads, but no opcode tables are bundled.
- PyPy/Jython/GraalPy variants are handled best-effort via the matching CPython version tables.

## Code layout

```
src/
  version.rs    magic table, version model, pyc header layout rules
  pyc.rs        pyc header parsing (8/12/16-byte, PEP 552 hash-based)
  marshal.rs    all-version marshal deserialization (v0–v5, FLAG_REF, interned tables, per-version code layouts)
  object.rs     PyObject model (incl. arbitrary-precision Long)
  code.rs       normalized CodeObject + 3.11+ exception-table parsing
  linetable.rs  lnotab / 3.10 linetable / 3.11+ position-table decoding
  opcode.rs     config loading (embedded + external overrides), canonical Op enum
  bytecode.rs   instruction decoding, jump normalization, disassembly rendering
  disasm.rs     recursive disassembly output
  ast.rs        version-independent AST
  decompiler.rs stack simulation + block-stack control-flow recovery (the core)
  codegen.rs    AST → source (precedence/indentation/version syntax differences)
  loader.rs     shared CLI loading logic
  bin/pycdas.rs disassembler entry point
  main.rs       decompiler entry point
configs/
  magics.json           magic → version
  opcodes/python_*.json per-version opcode/jump/arg-class/CACHE tables
tools/
  gen_configs.py        config generator (xdis + native interpreter export)
  dump_native.py        3.11+ native export script
  build_corpus.py       single-version corpus builder (2.6-compatible)
  build_corpus_all.py   all-version corpus build driver
  verify_corpus.py      corpus verification (decompile → recompile → signature/AST compare)
  sig_dump.py           structured bytecode signature export (run by the target-version interpreter)
  ast_compare.py        normalized-AST semantic comparison (2.6+ compatible)
tests/
  roundtrip.py          multi-version compile-decompile-recompile comparison matrix
  integration.rs        Rust integration tests (embedded fixtures)
  pyc/                  committed 2.7–3.14 test pycs
  fixtures/             test sources
```
